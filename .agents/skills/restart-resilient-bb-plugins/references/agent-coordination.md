# Long-running AI work in BB threads

Use an ordinary hidden coordinator child when the work needs judgment and may span many turns, but its state is recoverable from BB's own thread tree. The coordinator's thread ID is its run identity after creation. Give its initial prompt the complete request, execution settings, absolute targets, evidence rules, and final artifact path. Parent ordinary hidden workers to it (`originKind: null`); source-derived forks do not have the same parent-report contract. BB automatically reports a worker's turn to the parent, so a worker prompt need not ask it to `bb thread tell` the coordinator.

Prove that the coordinator's actual provider and permission mode can execute every required BB operation unattended before adopting a CLI-only protocol. In an isolated Perspectives run, Claude Code in `auto` requested approval for literal `bb thread show --self --json`, queue creation, hidden spawn, and `bb file write`; no operation ran while the approval was pending. A prompt granting authority does not change the provider's tool approval policy. If approval blocks required work, use scoped BB/plugin agent tools that implement the operations under an explicit trusted contract, or require an explicitly configured permission mode that permits them. Do not silently elevate a caller's permission mode to `full`, and do not count a full-mode proof as evidence that the default mode works.

For scoped tools, test **discovery and execution** in a real plugin-origin coordinator turn. Tool registration alone does not make a tool available: the plugin's agent configuration can suppress its own origin threads. BB's configuration callback is synchronous, so it cannot read persisted prompt identity there. Advertise the necessary tools without relying on a mutable title, then enforce the persisted run identity, direct parentage, and effect scope inside each tool handler. Verify that an ordinary worker cannot execute coordinator effects even if it can discover a tool.

Test the plugin's actual registration contract as well as its tool handlers. BB currently rejects a static agent-tool `instructions` string longer than 4096 JavaScript characters; a unit test of the handler can pass while the installed plugin exposes no tools. Keep registered instructions concise, put longer operating detail in a document or prompt where appropriate, and exercise installation in an isolated runtime before claiming the auto-mode path works.

Native reports are wake-ups, not the evidence record. BB batches them briefly in process memory and caps the output excerpt. On every report or timed wake, list all hidden children by parent ID, inspect their persisted statuses, and fetch full outputs by child ID. Match workers by fixed slot plus parent, not only a lens name or short excerpt. If a spawn or send response is ambiguous, discover the child or queue row before a permitted retry; unknown does not mean absent. BB's restart-resume plugin includes hidden threads but its automatic scan is selective, so it should supplement rather than own this recovery path.

For a worker spawn that may be retried on a later coordinator turn, persist a per-slot launch intent in a BB record **before** attempting the spawn. A re-list within the original turn is insufficient: a timed-out create can commit later, after that re-list. On the next wake, reconcile both the intent and committed children. If the intent exists but no child can be verified, freeze the slot as launch-uncertain or disclose possible duplicates; do not spawn it again just because the child list is empty. Remove temporary intent rows only after an immutable final result is read back, otherwise a restart can erase the fact that prevents blind replay.

When using the initial prompt as a run marker, verify that it is actually present in the API chosen for reconciliation. BB's prompt-history view filters agent-only accepted input; an isolated Perspectives coordinator's initial spawn prompt was absent there even though its first persisted `client/turn/requested` event held the full text. Use the earliest relevant thread event for exact prompt matching, and page or filter events explicitly when histories grow. Do not treat an empty prompt-history result as proof that a committed child has no matching initial request.

Keep the persisted run identity in a versioned, parseable part of that first request. Thread titles can be renamed, and regenerating an entire historical prompt with today's instructions can reject a valid run after a plugin update. Use title only to narrow discovery; verify the durable request and parent relationship before acting. Prompt text is durable evidence, not cryptographic provenance, so scope every tool effect to the invoking thread and its verified direct children.

Schedule only the wakes that close actual liveness gaps: for example, one wrap-up, one deadline, and a caller backstop. BB's `bb thread tell --send-at` stores a future queue row, but queue acceptance is not provider acknowledgement. A failed row may stop automatic dispatch and need explicit recovery; claims and offline hosts may delay delivery. Avoid a model turn every minute merely to replace an in-memory polling loop. On a delayed deadline wake, reconcile, bound unfinished worker work, and synthesize the available complete and partial evidence. State the actual timing limit.

Define what result status measures. A panel can completely answer “does the supplied evidence prove this?” with “no” and a list of missing evidence. That is different from proving the underlying claim. Mark a result partial when a requested analysis could not be performed or a worker output is unavailable; do not infer partial merely from a negative or uncertain substantive conclusion. Label any model judgment about evidence coverage separately from mechanical worker completion, and do not present it as verified fact.

Before creating workers, confirm every required coordinator wake or establish that its target has already passed. If one required row has a persisted dispatch failure, the other wake state is known, and BB records prove no worker launch was attempted, a failed no-research artifact can close the run. A missing or ambiguous row is a different outcome: leave launch uncertain and do not infer that no work occurred.

Store a long final answer in the coordinator's thread storage and put its thread ID, relative path, status, and a short digest-bearing summary first in the coordinator's final response. The parent report can be truncated; the caller must read the full file using the coordinator thread ID and verify its content before presenting it. Thread storage is per thread and host; a raw absolute path from a child is not automatically a local path for the caller. Distinguish missing, corrupt, and host-offline reads. Use operations available to the agent (often `bb` CLI or its local storage path); plugin SDK calls are not automatically available inside an ordinary agent thread.

Make the artifact checksum reproducible from a specified byte sequence. Define its encoding, exact body boundaries, newline handling, and terminal marker, or hash the full file and carry that digest outside the file. Compute and validate the checksum in product code when possible. A model's statement that it verified a digest is not evidence: in an isolated Perspectives run, the published `body_digest` matched neither plausible body slice, even though the whole file could be read successfully from another thread.

Check the actual file interface before promising atomic publication. In the current CLI, `bb file write` without `--expected-sha256` writes directly; the CLI cannot express the SDK's `expectedSha256: null` create-only request. An ordinary coordinator can write a uniquely named temporary file in the final directory, read it back and verify its digest, then make one `bb file move` to the final name and verify that readback. Do not retry an ambiguous final move before inspecting the final path. The move implementation checks destination absence separately from `rename`, so concurrent publishers can race, and it does not fsync the directory for power-loss durability. State those limits and prevent concurrent publishers for one run.

The thread-storage route resolves another thread's storage location by ID, but the current `bb file` CLI does not expose that lookup. A sibling storage path derived from the caller's environment is valid only when caller and coordinator share a host and storage root. If they differ, use an authorized route client or report retrieval unavailable; do not guess an absolute path.

Current BB does not expose a stable plugin-tool invocation ID across provider runtime reconstruction. A coordinator can be created and its spawn response lost; a replay may create another one. Return a launch receipt only after its thread ID and recovery wake are known. Otherwise say launch is uncertain, and make duplicate coordinator results inspectable rather than silently merging them. Do not add a plugin journal solely to promise exact one-per-call creation when BB cannot enforce it.

Check the order of those two launch effects. If the coordinator can be committed before the only caller wake is queued, a restart in that gap can leave a run with no durable caller reminder. Queue one backstop first with a fresh invocation marker, then spawn the coordinator with the same marker. On its eventual wake, the caller can discover zero, one, or multiple matching children and report that outcome; a successful launch receipt still requires a confirmed queue row and identified coordinator ID. Cancel a known unnecessary row after a definite launch rejection when safe, but retain it after an ambiguous spawn. This closes the ordering gap without adding a second journal or timer.

Retain the caller backstop after an artifact read. Verifying the file inside a tool call is not result presentation: deleting the backstop then creates a crash window in which the tool succeeds, the process stops before the caller answer is recorded, and no wake remains. A duplicate wake is preferable to silent loss. To reduce repeat presentation without a new journal, check the latest successfully completed caller turn and its final persisted agent message for an exact run ID and full-file digest receipt. An intermediate message, an interrupted turn, or a tool result is insufficient. If this evidence is absent, ambiguous, or unreadable, return the verified artifact again. This remains at-least-once delivery; a completed-turn receipt does not prove the human saw the answer or prevent every duplicate native notice.

## Proof matrix

For a live crash cut inside BB's queue claim, request commit, or process-local child-notice flush, a timed process kill may never hit the intended boundary. Use an opt-in fault barrier in a disposable runtime, record its observation with the queue/thread/event IDs, then stop that exact server process and restart against the same data. Keep the barrier disabled in normal startup. A unit test that pauses the handler proves the seam is reachable; only a process restart with persisted-state reconciliation proves recovery.

| Window | Required observation |
| --- | --- |
| Tool response lost after coordinator create | Child is rediscovered in the live invocation or launch is explicitly uncertain; no false success receipt. |
| Worker finishes before parent-notification flush, then host restarts | Scheduled wake finds persisted child and full output. |
| Coordinator is interrupted while workers run | Its next turn reconstructs workers and deadlines from BB records; no blind duplicate worker spawn. |
| Timed queue row is failed, claimed, or host-offline | Recovery or explicit bounded failure is visible; no claim of a strict deadline. |
| Synthesis file is written before final report, then host restarts | Caller backstop retrieves and verifies the one complete artifact by coordinator ID. |
| Final report or backstop arrives twice | Caller checks durable completed-turn presentation evidence before suppressing a repeated artifact body; without it, the artifact remains available and possible repeats are disclosed. Distinct runs remain separately inspectable. |

The Perspectives [restart plan](../../../../plans/perspectives-restart-resilience.plan.pkl) and [design](../../../../community-plugins/plugins/perspectives/COORDINATOR_DESIGN.md) are evolving case studies. Read their ledger before treating a planned guarantee as observed behavior.
