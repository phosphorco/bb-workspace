## Install the selected composition

Keep this directory alongside `plugins/` and `community-plugins/` when cloning or
transferring the workspace. Fork plugin manifests use a relative `file:` archive
pin; their lockfiles must be generated by the normal package manager. Published
SDK targets keep their exact registry versions. A standalone child checkout that
uses a fork archive needs that artifact at its declared relative path.

From the organization plugin root, use `bun install --frozen-lockfile`, then
`bun run sync:check` and `bun run sdk-types:check`. Typecheck, test, and build the
consumers before reloading them. The identity library retains its older SDK
support check; its private browser fixture package selects the fork explicitly.

Do not run `bb plugin types` to update a fork file pin. That command intentionally
repins package-based plugins to the CLI's SDK version. Use the workspace-selected package-layout-aware CLI for `bb plugin build`;
it preserves the installed dependency. Older CLIs may regenerate declaration
copies or stamp a different SDK version. Verify emitted metadata as well as
package resolution; the CLI package version is not its SDK version.

## Reproduce or advance the artifact

First materialize the exact selected source receipt and install its frozen lock.
Build the SDK through the supported pipeline from the core root:

```sh
pnpm exec turbo run build:types build --filter=@get-bb/plugin-sdk
```

Then, from the workspace root, pack into a fresh output directory:

```sh
node sdk-artifacts/prepare-plugin-sdk.mjs \
  --source fork/build/bb \
  --source-receipt c30b12255a7f9f098e7bf9b6d1999410e7956785 \
  --output /tmp/bb-sdk-reproduction
```

Compare the resulting archive SHA-256 with the selected receipt. The packer
requires built inputs and refuses to overwrite an existing artifact. It packs
public declarations and runtime files together, with unchanged exports and
optional peer contracts.

For a deliberate upgrade, use the new source receipt, preserve the old archive,
update the generator's exact file pin and checksum, and regenerate dependency
locks. Verify both package resolution and consumer behavior before removing any
old artifact that a lock still references. Publication is a separate action.
