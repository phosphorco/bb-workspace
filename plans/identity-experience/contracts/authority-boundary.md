## Revocation, accepted jobs and independent work

For **new** acceptance, expiry, abort, retired plugin/provider generation and relevant invalidation must prevent a late write. The invocation registry checks the current deadline on use, so an expired scope must not become valid merely because an asynchronous operation ignored cancellation. Provider registry resolution additionally checks its active epoch after awaiting the verifier. The selected [tests](/home/ubuntu/bb-service/fork/build/bb/apps/server/test/services/p6r/provider-registry.test.ts:97) describe late ignored-cancellation rejection; they were inspected, not executed in this turn.

For **already accepted** work, durable authorship and immutable operation outcome remain facts after the originating request ends. The [native contract](/home/ubuntu/bb-service/fork/plans/native-identity-settings-and-authorship.md:33) explicitly permits accepted queue snapshots to drain. Request expiry/revocation does not by itself cancel accepted jobs, recall an external send or rewrite authorship. Cancellation is a separate feature operation with its own accepted/too-late outcome. A policy that revocation also cancels queued or executing jobs must name which work, the enforcement point, race semantics and recovery behavior before implementation.

Independent background work uses explicit non-person/system or integration-origin behavior. Capturing a prior request's actor snapshot provides provenance only; it cannot authorize a fresh operation. Longer-lived on-behalf-of execution would require a separate grant contract, as [master §5.2](../../../fork/plans/bb-fork-master-plan.md:247) states.

## Requirements if Cole selects stronger scope

These are concrete design inputs, not newly claimed APIs or implicit campaign requirements.

1. **Scoped delegation.** Specify issuer/verifier authority, grant ID/version, subject/actor, intended service audience, allowed operation/resource set, instance/plugin binding, expiry, delegation depth/attenuation, revocation and replay policy. Bind the authorized immutable payload when accepting work. Retain an explicit distinction between authority to submit and authority to execute already accepted work. Decide whether collaborator-wide access remains the product rule; do not accidentally turn personal-state targets into private ACLs.
2. **Issuer trust.** If malicious-verifier resistance is required, define operator-controlled issuer ownership/key binding and replacement policy independently of provider declarations. Prove that a verifier cannot acquire another issuer namespace by declaring it. Changing stable person keys or issuer ownership requires legacy-owner mapping, held unresolved records and no fabricated identity recovery. If verifier correctness remains trusted, say so rather than adding unused cryptography.
3. **Process and filesystem powers.** Specify service UID/sandbox, readable/writable paths, executable/tool access, network egress, credential audience, IPC peer authentication and launch ownership. Keep machine-role/ingress deployment in rosetta-machine. An allowed-path list in docs is not enforcement. Negative probes must exercise the actual worker process and prove denied access to an isolated sentinel outside its grant, while valid work still succeeds; never use real private material as a test payload.
4. **Cross-process acceptance.** Replace in-memory scope/target identity with a reviewed protocol only when a real consumer needs it. Require authenticated transport and audience binding, immutable operation/payload identity, durable deduplication, expiry/revocation semantics evaluated at the authoritative commit point, and crash/retry/lost-response handling. A local preflight followed by an awaited remote write cannot claim the current synchronous commit guarantee. If revocation races with remote commit, specify a serializing authority/epoch or another concrete linearization rule and test it.

## Acceptance matrix for an expanded boundary

Use the actual host transport, package binding, feature storage and authoritative commit transaction. A schema-invalid fixture that fails before the intended boundary is not a valid negative witness. No test below is reported as run here.

| Witness | Required result |
| --- | --- |
| Genuine admitted request and direct untrusted request on selected ingress | Positive performs only allowed workflow; negative fails at admission with unchanged durable state. No fabricated-header substitute for genuine positive. |
| Known-valid operation paused after preflight; revoke/expire/retire before commit | Rejection at commit and unchanged record/receipt for unaccepted work. Repeat the same witness after any correction. |
| Fabricated scope/target; wrong instance/plugin/subject; changed immutable operation payload | Specific intended-boundary rejection; no side effect or fallback owner. Feature storage is real. |
| Request accepted, response lost, request expires, process restarts | Same operation reconciles to one durable outcome; no resend under a new ID. Accepted queue follows the explicitly chosen cancellation policy and retains original attribution. |
| External nickname matches a person; credential revoked before new submission | External namespace remains external; integration rejects invalid new authority. Existing accepted outcome remains distinguishable from a new send. |
| Verifier asserts undeclared issuer / lies within declared issuer | Undeclared issuer rejection is current mechanism; within-issuer assertion is trusted unless a separately selected issuer-proof design explicitly changes it. Do not make a misleading malicious-verifier test pass by malformed output. |
| Real isolated worker attempts forbidden path/credential/IPC audience | Selected OS/transport mechanism denies it; equivalent allowed work succeeds. Same-user clean environment alone is insufficient. |
| Remote process dies before/after durable commit; duplicate/reordered retry; revocation races with commit | One authoritative outcome under documented linearization and retention rules; unknown state stays uncertain, not silently accepted or resent. |

## Scope alternatives and cost

`separate-campaign` retains trusted-collaborator UX, current issuer trust, request/target lifecycle checks and feature-owned transaction validation. This campaign must still prove its accepted identity guarantees and fix real attribution/owner bugs; it cannot relabel a missing promised boundary as trusted behavior. Record the containment limitation in operator/provider docs and preserve a separate concrete security brief if desired.

`expand-this-campaign` adds only Cole-selected requirements from the preceding list. Root must revise graph, owners, write footprints and decisive live/transactional witnesses before work. Likely integration cost includes new transport/daemon/SDK seams, credential provisioning and service lifecycle, durable grant/revocation state, feature storage compatibility, and additional upstream revision/replay tests. Issuer-key changes and accepted-job policy changes can affect existing ownership and pending operations; require explicit migrations and interruption/recovery evidence. Do not estimate a schedule without choosing and probing the boundary.

The current architecture's upstream maintenance cost remains its small host-owned authority/lifecycle and transactional acceptance seams plus package/feature adapters. A new remote authority service is a materially different protocol with versioning and upgrade obligations. Keep product schemas outside core, use existing extension points first, and document deletion conditions for new seams.
