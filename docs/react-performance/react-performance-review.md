# Final adversarial review: React performance program

## Blocking issues

1. **The measurement claims are not auditable from the program.** The four documents repeat exact capture totals, but none links a raw React Scan export, run manifest, fixture hash, browser build, scenario script, or immutable artifact. The executive summary also adds claims not present in its own evidence tables: Automations is said to have zero settled renders, and the app-shell wrappers are said to have render-reason evidence, but no corresponding result is shown. The overlay diagnosis is plausible, but aggregate family names do not prove that per-message action bars caused the largest commits.

   **Exact edit:** add an `Evidence index` to the main program with local artifact paths and hashes for every quoted capture, including row/action/provider counts and the quiet controls. Delete `Automations` unless its capture is linked. Relabel “Populated-thread overlay multiplication” and the app-shell render-reason paragraph as hypotheses until commit-level counters/reasons are archived. Require E0 to fail if an evidence artifact or manifest is absent.

2. **The integration contribution is for a different, fork-wide store migration.** Its reactivity gate installs candidates in the **fork app**, benchmarks 1,200 thread summaries and S1/S2/S3/S6, then introduces a global D/L/T/P state graph. The consolidated program’s Track A is a **Thread Progress organization-plugin** clock, whose dependencies must be added to `plugins/tools/workspaces-sync/definition.ts` and generated with `bun run sync:fix`. These plans cannot both be executed. Local source confirms Thread Progress currently declares neither candidate, while TanStack 0.11.1 is merely transitive in `plugins/bun.lock`.

   **Exact edit:** replace the integration document’s “Reactivity-tool decision gate,” G/D/L/T/P table entries, and merge steps 2–6 with the plugin-local A0–A3/B1–B2 scope. Candidate dependencies belong in the Thread Progress definition plus the root catalog, not `fork/build/bb/apps/app/package.json` or `pnpm-lock.yaml`. Keep a separate fork dependency gate only if a later, independently approved fork-wide migration exists. In the main program, state that B2 is a fork host/SDK track and A/B1 are plugin tracks; do not describe them as one dependency owner.

3. **The TanStack recommendation contradicts its own hard architecture rule.** The program forbids a custom listener registry or parallel reactive engine and says the selected library must own subscriptions. The proposed TanStack design then relies on a plugin-owned keyed `Map<ThreadId, TemporalSource>`, reference-counted custom `subscribe`, eviction, heap registration, and publication. The sidebar contribution itself notes that TanStack Store exposes no first/last-subscriber lifecycle hook. As written, A0 can ratify TanStack only by implementing the adapter the program rejects. Conversely, Effect 4 in the workspace is not a direct Thread Progress runtime dependency; the cited effect-atom peer mismatch establishes duplicate/version-line risk, not by itself that a separately resolved compatible runtime cannot build.

   **Exact edit:** before naming a winner, define an allowed adapter boundary. The library must own snapshot storage, equality, batching, and React notification; a small scheduler resource manager may own deadlines and keyed lifetime, with no second value graph. Add a prototype assertion showing publications flow through the candidate library and that the adapter contains no independent listener fan-out. If TanStack cannot meet deterministic first/last-subscriber cleanup within that boundary, select effect-atom or explicitly relax the prohibition through an ADR. Change “current `@effect-atom/atom-react@0.7.0`” to “the evaluated 0.7.0 candidate,” and make exact lock resolution, peer installation, bundle closure, and build results—not an inferred mismatch—the compatibility gate. Until A0 produces that evidence, change the main recommendation to “undecided; TanStack is the leading candidate.”

4. **The temporal design silently changes accessibility semantics.** Current source updates `role="timer"` `aria-label` and `title` with `statusText(..., now)`, whose live description includes exact seconds. The proposal says to bucket the description with visible text or refresh it only on focus. That is a product/accessibility behavior change, yet the goals promise preservation. It also makes “10 seconds with no meaningful deadline” misleading for ordinary active/idle rows: exact-second accessible text currently has a meaningful deadline every second.

   **Exact edit:** add an A1 decision test for the timer’s accessible-name/title contract. Either preserve exact seconds as a narrow leaf deadline and budget the 200-row simultaneous second boundary, or obtain an explicit reviewed semantic change with screen-reader tests and documentation. Rename the zero-work scenario to “10 seconds with only static rows and no presentation/accessibility/section deadline.” Define the disposal grace period before asserting zero keyed sources; immediate zero conflicts with the proposed short eviction delay and Strict Mode unsubscribe/resubscribe cycles.

5. **Fork ownership is unsafe and incomplete.** B2, C, and D change fork code, but the plan names `fork/build/bb` components as owner surfaces and never says durable edits must be exported into `fork/patches/series`. `fork/README.md` says `build/bb` is disposable and durable changes are patches. The populated-thread contribution cites `fork/upstream` even though the deployed `fork/build/bb` tree differs in `ThreadTimelineRows.tsx` and `ThreadDetailView.tsx`; line references are consequently not references to the tested composition.

   **Exact edit:** add a fork-track ownership rule: inspect/edit in an approved temporary materialization/worktree, export reviewed commits into the ordered patch series, refresh patch hashes/result-tree lock, rematerialize, and run verify/namespace gates; never make durable edits in `build/bb` or the pinned upstream submodule. Change material source citations to the exact materialized result tree (plus result-tree SHA) or cite both upstream and the downstream patch that changes it. Assign one fork patch-series owner across B2/C/D.

6. **There is no single benchmark protocol, so budgets are incompatible.** The thread contribution requires two warm-ups plus 10 measured warm runs, median/p90, while integration and the main program require one warm-up plus seven runs, median/p95. The original Thread Progress fixture is 1440×1000, while E pins 1440×900. C budgets use p90 while the general lane uses p95. “5% or 2 MiB” heap tolerance and the main program’s relative/absolute wording do not define an unambiguous fail predicate.

   **Exact edit:** make E0 the sole protocol and have all tracks reference it. Choose one sample count and percentile (recommended: retain 7 samples and p95 only if the baseline proves the estimate stable; otherwise increase the count), and delete contradictory T0 numbers. Keep two explicitly named desktop cells if both viewports are necessary: TP-200 at 1440×1000 for historical comparability and HOST-THREAD at 1440×900; never compare their absolute counts. Define each regression predicate algebraically, including heap (for example, fail only when both `delta > 5%` and `delta > 2 MiB`). State whether C1/C2/C3 thresholds are medians, p95s, or per-run maxima and which frozen baseline they use.

7. **The advertised parallelism has unresolved file/API ownership and contradictory ordering.** The main checklist starts Track D in the parallel phase although its own Track D says it begins only after C is stable. C1 and C2 are said to develop concurrently while both integrate through `MessageActionBar.tsx`; “single ownership” does not make two concurrent writers safe. B2 may be internal or a public experimental SDK change, but that decision is left open even though A3 and plugin consumers depend on it. The plan also defers typecheck/build chiefly to final integration, allowing branches to diverge before basic gates run.

   **Exact edit:** remove D from the initial parallel implementation list; only attribution instrumentation may start early, while D implementation waits for the post-C profile. Give C1 ownership of the timeline provider boundary and C2 ownership of a shared lazy-overlay primitive, with one named integrator applying/serializing their `MessageActionBar.tsx` call-site changes; otherwise land C1 before C2. Resolve B2 before implementation: prefer an internal shared cache with the existing SDK contract; if a new public member is required, name it `experimental_`, add `docs/api_to_audit.md`, regenerate SDK types, and land fork/API before plugin use. Add per-track affected-package typecheck, focused test, and production build gates before handoff, while retaining the full combined gates at the end.

## Optional refinements

- Replace “four duplicate maps per mounted row” with a bounded, source-derived statement. The current component shape supports up to four map-building hook paths per row (three action calls plus split), but the exact runtime count should be measured because React composition and snapshot identity determine when each memo recomputes.
- Treat the exact C1/C2 percentage improvements as provisional ratchets until E0 establishes variance and provider/action counts. A correct provider hoist should not be rejected merely because providers represented less than the assumed 8% of total records; require the targeted reduction plus no production regression first, then freeze an evidence-based total-record target.
- Add browser/version ownership to C3 rollout. The contributor requires Chromium, Firefox, and Safari/iOS, while E only pins Chromium. Keep Chromium as the performance gate and name Firefox/Safari/iOS as mandatory correctness cells with owners and supported host/CI environments.
- Add explicit timer-clamping, system sleep/resume, backward/forward wall-clock jump, and stale heap-entry generation tests to A2; fake-clock calculator tests alone do not validate browser scheduling lifecycle.
- Clarify that React Scan callback counts are “render callbacks/records,” not synonymous with component renders or fibers, throughout the quantitative budgets.

## Verdict

**Not ready to execute.** The root-cause prioritization is credible and the correctness matrix is strong, but the program currently combines two incompatible scopes, recommends a TanStack architecture forbidden by its own rules, changes timer accessibility without approval, lacks a single benchmark contract, and does not respect the fork’s durable patch ownership model. After the seven blocking edits above—especially a scoped A0 ADR/prototype and one authoritative E0 protocol—the implementation tracks can start safely and in genuine parallel.

## Re-review after corrections

All seven findings are resolved enough to begin **E0 and A0 only**:

1. Historical measurements are explicitly unaudited; E0 must reproduce and archive them before they become baselines.
2. The fork-wide store migration is marked superseded, and A0 is correctly plugin-local.
3. TanStack is only the leading candidate; the permitted scheduler boundary and library-owned publication rule are explicit.
4. Exact-second accessible text is preserved unless separately reviewed, and disposal grace is defined.
5. The fork patch-series/result-tree rule is explicit for product tracks.
6. E0 is the sole sampling protocol, with separate viewports and algebraic failure predicates.
7. D is deferred, C shared-file integration is serialized, B2 defaults internal, and track-local build gates are present.

One operational condition remains before either foundation track writes tracked files: extend the fork durability rule to any E0 profiling bootstrap/build/harness change under `fork`, or state that E0 is entirely out-of-tree; and isolate A0 dependency experiments from the currently dirty `plugins/package.json`, `plugins/bun.lock`, and `plugins/tools/workspaces-sync/definition.ts` without discarding or contaminating that authored work. Out-of-tree prototypes and read-only E0 reproduction may start immediately. No selected dependency, adapter skeleton, production hook, or baseline ratchet should land until E0 artifacts and the A0 ADR are reviewed.

**Verdict:** ready to start E0 evidence/harness work and A0 isolated prototyping, subject to the write-ownership condition above. Product implementation remains blocked.
