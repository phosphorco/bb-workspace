Interactive field guide · for veteran SDK designers

BB is an extension language with a host around it.

The plugin SDK is not one oversized callback. It is a set of deliberately different seams: durable state, product surfaces, supervised execution, agent affordances, and signals. Learn to place a need in the right seam—and the rest of the architecture starts to feel inevitable.

01 · mental model

Think in placements, not features.

A plugin is a small product distributed across runtimes. Click a placement to see what it owns and what it deliberately does not own.

Select a placement

The host is the composition root.

BB gives each runtime the smallest useful vocabulary for its job. A plugin can cross the boundary through typed contracts, but it does not blur the boundary.

Design heuristic: if your new capability needs a database, an interactive surface, and a third-party API, that is three placements joined by one contract—not one giant plugin function.

03 · the need taxonomy

Four core needs—and one important fifth.

Persistence, extension, attachment, and communication are the recurring categories. Execution is the fifth: it explains why BB separates a host worker from a server request.

Persist what the user can come back to.

Use the lightest durable store that matches the data. JSON KV is namespaced and bounded; plugin SQLite handles relational or indexed records; thread storage is for user-visible files attached to a thread.

The key design move is ownership: a plugin owns its namespace and migrations. The host owns the location, permissions, lifecycle, and cleanup.

Extend through additive slots.

Most plugin surfaces are additive: a homepage section, settings section, nav panel, thread action, composer action, message action, command palette item, file opener, or content script.

Replacement is intentionally rarer. When a plugin replaces a built-in renderer or thread list, the original is available through an explicit experimental delegation path.

Attach context at the moment it becomes useful.

Mentions are a particularly revealing API: search while the user types, then resolve the selected item at send time. The plugin can attach hidden, agent-only context without changing the visible message.

Other attachment points include timeline items, composer data, navigation params, and message directives. Each keeps ownership with the plugin while the host owns the surrounding interaction.

Match the communication channel to its truth.

RPC is a validated request/response boundary. Realtime is a best-effort, ephemeral signal. Lifecycle events are observation hooks, not veto points. HTTP is for outside callers and signed webhooks.

This separation prevents a common SDK failure mode: treating an event bus as a database, or treating a websocket as an API that must never lose a message.

Put long-lived or privileged work in the right runtime.

A host worker is optional, supervised, digest-verified, and given a typed bridge. It is the right home for provider integrations, filesystem work, local processes, and network loops that should not live inside a request handler.

Runtime identity is minted by BB, not guessed by a plugin. That keeps provider events attributable to real threads, agents, and users.

04 · highest-leverage choices

The SDK’s philosophy is encoded in the constraints.

The most important choices are not the number of methods. They are the handful of boundaries that make composition legible, failures local, and upgrades survivable.

01

Plain-data descriptors

Settings and registration metadata can be rendered by the host, exposed in CLI, and inspected without executing plugin code. A descriptor is an integration surface, not decoration.

02

Schema at every RPC edge

Standard Schema-compatible inputs and outputs turn runtime boundaries into contracts. Invalid input, handler failure, non-JSON output, and unknown method have stable meanings.

03

Observe, don’t intercept

Lifecycle events are fire-and-forget and cannot veto core actions. Plugins can react to thread changes without becoming hidden middleware in BB’s critical path.

04

Durable vs ephemeral

KV, SQLite, and thread files persist. Realtime does not. The API makes the developer decide whether a client should refetch or reconstruct.

05

Wholesale registration

Reload registers a candidate as a unit. If it fails, the old plugin stays live; if it succeeds, services stop, disposers run in reverse order, and stale handles become invalid.

06

One capability, many doors

A search function can feed a tool, a CLI command, a mention resolver, and a KV cache. The SDK makes these doors explicit without forcing one UX on every plugin.

01 · App

User clicks Save; app sends a typed RPC request.

02 · Server

Host validates input; plugin writes owned durable state.

03 · Signal

Plugin publishes a small realtime invalidation.

04 · App

Every open client refetches through the same RPC.

Notice what is absent: the realtime payload is not the record. It is a hint that the record may have changed.
05 · concrete compositions

Read the plugin as a small system.

These are compact shapes from the BB examples and Phosphor plugins. The point is not memorizing APIs; it is seeing how one responsibility crosses several explicit seams.

Example 1 · one search function, four agent-facing doors

In examples/plugins/agent-enrichment/server.ts, search is a capability. The plugin reuses it for a CLI command, an agent tool, a mention resolver, and a KV-backed enrichment path. Configure the tool and skill only when the relevant setting is enabled.

illustrative shape · capability fan-out
const search = async (query: string) => index.lookup(query);

api.cli.register({ name: "search", run: ({ args }) => search(args.query) });
api.agents.registerTool({ name: "search_context", input: querySchema, execute: search });
api.agents.registerMention({ name: "doc", search, resolve: attachAgentContext });
api.storage.kv.set("last-search", { query, resultCount });
Example 2 · Thread Links: durable index + RPC + invalidation

plugins/thread-links/server.ts creates an owned SQLite index, exposes list/create/delete RPC methods, and publishes a realtime change. Its app counterpart adds a thread-header action, then refetches on realtime and reconnect.

illustrative shape · durable feature
await db.migrate();
api.rpc.register("links.list", listInput, listOutput, async ({ input }) => db.list(input.threadId));
api.rpc.register("links.create", createInput, linkOutput, async ({ input }) => {
  const link = await db.create(input);
  api.realtime.publish({ channel: "links.changed", payload: { threadId: input.threadId } });
  return link;
});
Example 3 · Slack bot: signed ingress + mapping + thread lifecycle

examples/plugins/slack-bot/server.ts combines declarative settings, a signed HTTP webhook, namespaced KV for Slack-to-BB mapping, thread spawn/send, and an idle reply. The request handler is small because the durable mapping and thread system carry the state.

illustrative shape · outside communication
api.http.route({ method: "POST", path: "/events", auth: "none" }, async (request) => {
  if (!verifySlackSignature(request)) return unauthorized();
  const bbThread = await findOrSpawnThread(api.storage.kv, event.channel);
  await api.threads.send(bbThread.id, renderInboundMessage(event));
  return ok();
});
Example 4 · composer customization: additive UI, host-owned send

examples/plugins/composer-customization/app.tsx adds an action, plus-menu item, banner, rich-text effect, and draft observer. It can shape the composer without reimplementing thread loading, streaming, permissions, queueing, or send/stop behavior owned by ThreadChat.

illustrative shape · additive app surface
api.ui.composer.register({
  action: ({ composer }) => composer.insertText("/summarize "),
  plusMenu: { label: "Insert template", onSelect: insertTemplate },
  banner: ({ thread }) => thread ? "Plugin context active" : null,
  onDraftChange: draft => api.storage.kv.set("draft-length", draft.length)
});

07 · architecture recipes

Three recipes worth carrying into design review.

A

Durable collaborative feature

SQLite → RPC → app slot → realtime invalidation. Add reconnect refetch and thread-deletion cleanup. Keep the payload small and the record durable.

B

External integration

settings → signed HTTP / host worker → mapping KV → threads API. Add a background outbox when delivery must retry, and surface configuration errors explicitly.

C

Agent-native capability

tool + skill + mention resolver + CLI. Reuse one domain function; make context selection static where possible and dynamic only where necessary.

What does the plugin SDK refuse to hide?

It makes auth mode, input/output schemas, settings shape, storage ownership, lifecycle cleanup, realtime ephemerality, and reload behavior explicit. These are exactly the places where an extension platform otherwise accumulates accidental policy.

Why only a few host-owned React components?

BB owns the high-value orchestration component—ThreadChat—and the Markdown contract. Plugins bring their own UI primitives. That keeps the host/plugin boundary stable while letting plugin experiences evolve independently.

How do I know whether I need a host worker?

If the work is request-shaped and fast, keep it server-side. If it is long-lived, provider-facing, filesystem-bound, or needs supervised restart behavior, put it in the optional host runtime and expose a typed contract back to the server.
